# ADR-009 아웃박스(CDC) 모양 출력

- 상태: 제안
- 날짜: 2026-10-27

## 맥락

Kafka 출력(ADR-007)은 업무 이벤트(봉투 JSON)를 그대로 토픽에 넣는다. 실제 조선소의 MES·ERP 데이터는 이렇게 깔끔하게 오지 않는 경우가 많다. 흔한 경로는 업무 트랜잭션과 함께 `outbox` 테이블에 이벤트 행을 쓰고, Debezium 같은 CDC 커넥터가 그 테이블의 변경을 Kafka로 옮기는 것이다(아웃박스 패턴).
플랫폼이 이 경로의 수집을 연습하려면, 토픽에 CDC 변경 이벤트 모양의 메시지가 들어와야 한다.

선택지는 셋이다.

| 안 | 토픽에 들어오는 것 | 플랫폼이 연습하는 것 | 비용 |
| --- | --- | --- | --- |
| A. 이벤트 라우터 적용 뒤 | Debezium Outbox Event Router가 풀어 준 업무 이벤트. 키 = aggregateid | 지금과 거의 같음 | 낮음, 얻는 것도 적음 |
| B. 아웃박스 테이블 원본 CDC | 변경 이벤트(`before`·`after`·`source`·`op`), `after.payload`는 문자열 | 봉투 풀기, `op` 거르기, 키·파티션과 순서, `id`로 중복 제거 | 중간: 출력 변환 하나 |
| C. 상태 테이블 CDC | `blocks`·`hulls` 같은 상태 테이블의 행 변경 | 상태 차이 → 이벤트 복원, 이력 관리 | 높음: 시뮬레이터에 테이블 모델이 필요하고 정답과의 대응이 달라짐 |

진짜 Postgres + Debezium을 띄워 방출기가 테이블에 쓰게 하는 방법도 있다. 가장 실제와 같지만 Debezium이 `ts_ms`를 실제 시계로 찍어 가상 시계(ADR-002)와 재현성이 깨지고, 개발 환경이 무거워진다.

## 결정

B를 택한다. 방출기가 CDC 커넥터가 낼 메시지를 직접 만든다. 실제 Debezium은 쓰지 않는다.

1. **출력 방식**: `--sink kafka --format outbox`. 기본은 지금의 `envelope`. 아웃박스 모양은 Kafka 출력에만 있다. 파일 모드와 채점용 사본(`--copy-dir`)은 봉투 그대로라 리포트는 바뀌지 않는다.
2. **아웃박스 테이블**: 출처 시스템(erp·mes·eam)마다 DB가 하나씩 있고, 각 DB에 `public.outbox` 테이블이 있다고 본다. 행 하나 = 방출 이벤트 하나.

   | 열 | 값 |
   | --- | --- |
   | `id` | `event_id` |
   | `aggregatetype` | `entity_key`의 종류. `event_type`의 대상으로 정한다: `order.*`·`hull.*` → `hull`, `block.*` → `block`, `equipment.*` → `equipment`, `system.manifest_published` → `manifest` |
   | `aggregateid` | `entity_key` |
   | `type` | `event_type` |
   | `payload` | 봉투에서 `emitted_at`을 뺀 JSON 문자열. 원천 DB는 도착 시각을 모른다 |

   수주(`order.contracted`)의 `entity_key`는 호선 번호라 `hull`이다(ADR-006 결정 2). 마감 집계(ADR-006)도 같은 테이블로 보낸다. 노이즈가 없는 것은 그대로다.
3. **토픽과 키**: Debezium 기본 이름인 `<source>.public.outbox`(예: `mes.public.outbox`). 키는 테이블 기본 키 `{"id": "<event_id>"}`다. 그래서 같은 개체도 여러 파티션에 흩어진다. ADR-007 결정 3(키 = `entity_key`, 같은 개체는 같은 파티션)과 다른 점이고, 의도한 것이다. 개체 순서는 `seq`나 `source.lsn`으로 플랫폼이 다시 맞춘다. 실제 원본 CDC에서 흔히 부딪히는 문제라 그대로 둔다.
4. **값: 변경 이벤트**(JSON 변환기, `schemas.enable=false` 모양)

   ```json
   {"before": null,
    "after": {"id": "01a19957-…", "aggregatetype": "hull", "aggregateid": "H-2602",
              "type": "order.contracted", "payload": "{\"event_id\":\"01a19957-…\",…}"},
    "source": {"connector": "postgresql", "db": "erp", "schema": "public", "table": "outbox",
               "lsn": 1, "txId": 1, "ts_ms": 1793574004000},
    "op": "c", "ts_ms": 1793574004000}
   ```

   - `source`는 Debezium의 필드 중 위 일곱 개만 흉내 낸다. `version`, `name`, `snapshot`, `sequence`, `xmin` 등은 넣지 않는다.
   - `source.ts_ms`(커밋 시각)와 `ts_ms`(커넥터 처리 시각)는 둘 다 `emitted_at`이다. ADR-005의 지연은 현장 입력이 늦은 것, 곧 원천 DB에 늦게 커밋된 것으로 읽는다. 복제 지연은 따로 두지 않는다.
   - `source.txId`: 출처 시스템별로 1부터 늘어나는 번호. 아웃박스 행 하나 = 트랜잭션 하나다.
   - `source.lsn`: 출처 시스템별로 1부터 늘어나는 번호. 변경 하나(넣기·지우기)마다 하나씩 쓴다.
   - **번호는 이벤트가 힙에서 처음 꺼내질 때(첫 도착) 매긴다.** 그래서 `lsn`·`txId` 순서가 `ts_ms`(커밋 시각) 순서와 같다. 정답을 읽는 순서(힙에 넣을 때)로 매기면 늦게 도착한 이벤트가 작은 `lsn`에 큰 `ts_ms`를 갖게 되어 커밋 순서와 어긋난다.
   - 중복 사본(ADR-005의 재시도)은 새 번호를 받지 않고 원본의 번호를 그대로 쓴다. 커넥터가 같은 변경을 다시 보낸 것이기 때문이다. 원본과 사본은 힙에서 같은 이벤트 객체를 가리키므로, 원본을 꺼낼 때 매긴 번호를 그 객체에 적어 두면 사본도 같은 번호를 본다.
   - 메시지 타임스탬프는 `emitted_at`(ADR-007과 같다). 중복 사본도 ADR-005대로 같은 `emitted_at`이다.
5. **지우기**: 아웃박스 행은 보통 넣은 트랜잭션 안에서 바로 지운다. 그래서 행마다 메시지 셋을 이 순서로 보낸다.

   | 순서 | 메시지 | `op` | `before` | `after` | `lsn` | `txId` |
   | --- | --- | --- | --- | --- | --- | --- |
   | 1 | 넣기 | `c` | null | 행 | n | t |
   | 2 | 지우기 | `d` | `{"id"}`만 있고 나머지 열은 null | null | n + 1 | t |
   | 3 | 툼스톤 | 값 null | | | | |

   - 지우기의 `before`는 Postgres 기본 설정(`REPLICA IDENTITY DEFAULT`)을 흉내 내 기본 키만 담는다. 행 전체가 필요하면 `FULL`을 흉내 내는 설정을 따로 둔다.
   - 셋 모두 같은 키(`{"id"}`), 같은 메시지 타임스탬프다. 툼스톤은 Debezium 기본값(`tombstones.on.delete=true`)을 따른다.
   - 중복 사본은 셋을 모두 같은 번호로 다시 보낸다. 커넥터는 마지막 오프셋 뒤의 변경을 트랜잭션 단위로 다시 보내기 때문이다.
   - 플랫폼은 `op: "d"`와 툼스톤을 걸러야 한다. 메시지 수는 세 배가 된다.
6. **노이즈와 마감 집계는 같다**: 이벤트별 지연·중복·누락(ADR-005)을 그대로 쓴다. 그래서 모양만 바꿔도 같은 채점으로 비교할 수 있다.
   - 누락은 "원천은 업무 트랜잭션과 함께 아웃박스에 썼지만, 커넥터·복제 구간에서 빠진 것"으로 읽는다. 원천은 쓴 것으로 알기 때문에 마감 집계(ADR-006)에 들어간다. 지금 마감 집계가 전송 중 빠진 이벤트도 "보낸 것"으로 세는 것과 같다.
   - 아웃박스 패턴은 업무 행과 아웃박스 행을 한 트랜잭션으로 써서 "업무는 됐는데 아웃박스에 없음"을 막는다. 그래서 원천이 아웃박스에 쓰지 않은 것으로 읽지 않는다.
   - 정상적으로 돌아가는 Debezium은 커밋된 변경을 잃지 않는다. 여기서는 복제 슬롯을 잃거나 다시 만들 때처럼 드문 손실을 흉내 낸 단순화다.

## 결과

- 플랫폼은 같은 노이즈를 세 모양(파일, 봉투 Kafka, CDC Kafka)으로 받아 볼 수 있다.
- 플랫폼이 할 일이 늘어난다: `after.payload` 풀기, `op: "d"`와 툼스톤 거르기, 파티션에 흩어진 개체 순서 맞추기, `id`로 중복 제거.
- 체크포인트(ADR-007)에 출처 시스템별 `lsn`·`txId` 카운터를 더한다. 원본만 체크포인트 전에 나가고 사본은 힙에 남은 경우에도 원본 번호가 유지되어야 하므로, 힙의 이벤트 객체에 적은 번호도 함께 저장한다. 원본과 사본이 같은 객체라는 것은 한 번에 직렬화하면 유지된다. 상태 모양이 바뀌므로 체크포인트 `VERSION`을 올린다.
- 번호는 Kafka 출력 안에서만 쓴다. 채점용 사본과 파일 출력의 봉투에는 들어가지 않는다.
- 다루지 않는 것
  - C안(상태 테이블 CDC): 플랫폼의 상태 기반 수집 연습이 필요해지면 따로 ADR을 쓴다.
  - 커넥터 재시작 때 마지막 커밋 오프셋부터 몰려서 생기는 중복: 지금 중복은 이벤트마다 따로 생긴다. 몰린 중복이 필요하면 노이즈 종류를 더한다.
  - 스키마 레지스트리와 Avro, 아웃박스로 보내는 재발행.
