# ADR-009 아웃박스(CDC) 모양 출력

- 상태: 제안
- 날짜: 2026-10-27

## 맥락

Kafka 출력(ADR-007)은 업무 이벤트(봉투 JSON)를 그대로 토픽에 넣는다. 실제 조선소의 MES·ERP 데이터는 이렇게 깔끔하게 오지 않는 경우가 많다. 흔한 경로는 업무 트랜잭션과 함께 `outbox` 테이블에 이벤트 행을 쓰고, Debezium 같은 CDC 커넥터가 그 테이블의 변경을 Kafka로 옮기는 것이다(아웃박스 패턴).
플랫폼이 이 경로의 수집을 연습하려면, 토픽에 CDC 변경 이벤트 모양의 메시지가 들어와야 한다.

선택지는 셋이다.

| 안 | 토픽에 들어오는 것 | 플랫폼이 연습하는 것 | 비용 |
| --- | --- | --- | --- |
| A. 이벤트 라우터 적용 뒤 | Debezium Outbox Event Router가 풀어 준 업무 이벤트. 키 = aggregateid | 지금과 거의 같음 | 낮음, 얻는 것도 적음 |
| B. 아웃박스 테이블 원본 CDC | 변경 이벤트(`before`·`after`·`source`·`op`), `after.payload`는 문자열 | 봉투 풀기, `op` 거르기, 키·파티션과 순서, `id`로 중복 제거 | 중간: 출력 변환 하나 |
| C. 상태 테이블 CDC | `blocks`·`hulls` 같은 상태 테이블의 행 변경 | 상태 차이 → 이벤트 복원, 이력 관리 | 높음: 시뮬레이터에 테이블 모델이 필요하고 정답과의 대응이 달라짐 |

진짜 Postgres + Debezium을 띄워 방출기가 테이블에 쓰게 하는 방법도 있다. 가장 실제와 같지만 Debezium이 `ts_ms`를 실제 시계로 찍어 가상 시계(ADR-002)와 재현성이 깨지고, 개발 환경이 무거워진다.

## 결정

B를 택한다. 방출기가 CDC 커넥터가 낼 메시지를 직접 만든다. 실제 Debezium은 쓰지 않는다.

1. **출력 방식**: `--sink kafka --format outbox`. 기본은 지금의 `envelope`. 아웃박스 모양은 Kafka 출력에만 있다. 파일 모드와 채점용 사본(`--copy-dir`)은 봉투 그대로라 리포트는 바뀌지 않는다.
2. **아웃박스 테이블**: 출처 시스템(erp·mes·eam)마다 DB가 하나씩 있고, 각 DB에 `public.outbox` 테이블이 있다고 본다. 행 하나 = 방출 이벤트 하나.

   | 열 | 값 |
   | --- | --- |
   | `id` | `event_id` |
   | `aggregatetype` | `entity_key` 종류: 호선 `hull`, 설비 `equipment`, 마감 집계 `manifest` |
   | `aggregateid` | `entity_key` |
   | `type` | `event_type` |
   | `payload` | 봉투에서 `emitted_at`을 뺀 JSON 문자열. 원천 DB는 도착 시각을 모른다 |

   마감 집계(ADR-006)도 같은 테이블로 보낸다. 노이즈가 없는 것은 그대로다.
3. **토픽과 키**: Debezium 기본 이름인 `<source>.public.outbox`(예: `mes.public.outbox`). 키는 테이블 기본 키 `{"id": "<event_id>"}`다. 그래서 같은 개체도 여러 파티션에 흩어진다. 개체 순서는 `seq`나 `source.lsn`으로 플랫폼이 다시 맞춘다. 실제 원본 CDC에서 흔히 부딪히는 문제라 그대로 둔다.
4. **값: 변경 이벤트**(JSON 변환기, `schemas.enable=false` 모양)

   ```json
   {"before": null,
    "after": {"id": "01a19957-…", "aggregatetype": "hull", "aggregateid": "H-2602",
              "type": "order.contracted", "payload": "{\"event_id\":\"01a19957-…\",…}"},
    "source": {"connector": "postgresql", "db": "erp", "schema": "public", "table": "outbox",
               "lsn": 1, "txId": 1, "ts_ms": 1793574004000},
    "op": "c", "ts_ms": 1793574004000}
   ```

   - `source.ts_ms`(커밋 시각)와 `ts_ms`(커넥터 처리 시각)는 둘 다 `emitted_at`이다. ADR-005의 지연은 현장 입력이 늦은 것으로 읽는다. 복제 지연은 따로 두지 않는다.
   - `source.lsn`, `txId`: 출처 시스템별로 1부터 늘어나는 번호이고, 이벤트가 처음 나간 순서로 매긴다. 중복 사본(ADR-005의 재시도)은 원본의 번호를 그대로 쓴다. 커넥터가 같은 변경을 다시 보낸 것이기 때문이다.
   - 메시지 타임스탬프는 `emitted_at`(ADR-007과 같다).
5. **지우기**: 아웃박스 행은 보통 쓴 직후 지운다. 그래서 행마다 `op: "c"` 다음에 `op: "d"`(`before`에 행, `after`는 null)와 툼스톤(같은 키, 값 null)을 함께 보낸다. 플랫폼은 이것을 걸러야 한다. 메시지 수는 세 배가 된다.
6. **노이즈와 마감 집계는 같다**: 이벤트별 지연·중복·누락(ADR-005)을 그대로 쓴다. 누락은 "원천이 아웃박스에 쓰지 않음"으로 읽는다. 그래서 모양만 바꿔도 같은 채점으로 비교할 수 있다.

## 결과

- 플랫폼은 같은 노이즈를 세 모양(파일, 봉투 Kafka, CDC Kafka)으로 받아 볼 수 있다.
- 플랫폼이 할 일이 늘어난다: `after.payload` 풀기, `op: "d"`와 툼스톤 거르기, 파티션에 흩어진 개체 순서 맞추기, `id`로 중복 제거.
- 체크포인트(ADR-007)에 출처 시스템별 `lsn` 카운터를 더한다. 중복 사본이 원본 번호를 쓰려면 번호를 힙 항목에 함께 담아야 한다. 원본만 체크포인트 전에 나간 경우에도 번호가 유지되게 하기 위해서다.
- 다루지 않는 것
  - C안(상태 테이블 CDC): 플랫폼의 상태 기반 수집 연습이 필요해지면 따로 ADR을 쓴다.
  - 커넥터 재시작 때 마지막 커밋 오프셋부터 몰려서 생기는 중복: 지금 중복은 이벤트마다 따로 생긴다. 몰린 중복이 필요하면 노이즈 종류를 더한다.
  - 스키마 레지스트리와 Avro, 아웃박스로 보내는 재발행.
