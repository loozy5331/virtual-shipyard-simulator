# ADR-012 컨테이너와 재발행 요청 디렉터리

- 상태: 확정
- 날짜: 2026-10-27

## 맥락

플랫폼은 docker compose 하나로 뜨고, 원천도 `source` 프로필로 같이 띄우려 한다(플랫폼 계획 0단계). 지금 원천은 호스트에서 `uv run`으로만 돈다.
재발행(ADR-006·008)은 사람이 `emitter.replay --requests FILE --at 시각`을 치는 명령이다. 플랫폼 4단계(11/13)는 대사로 찾은 누락을 공유 디렉터리 `requests/`에 쓰고, 원천이 알아서 다시 보내 주기를 기대한다. 플랫폼은 원천 코드를 실행하지 않는다.
명령으로 재발행할 때는 사람이 처리 시각(`--at`)을 골랐다. 서비스로 돌면 고를 사람이 없다.

## 결정

1. **이미지 하나, 명령 셋**: `Dockerfile` 하나가 `sim`, `emitter`(`--sink kafka`), `emitter.replay_service`를 모두 담는다. 코드와 `params/`·`schemas/`가 같아 이미지를 나눌 까닭이 없다. 선택 의존성 `kafka`를 넣고, 작업 디렉터리 `/app`의 `out/`에 쓴다(볼륨은 `/app/out`).
2. **재발행 서비스**(`python -m emitter.replay_service`): 요청 디렉터리를 `--interval`(기본 5초)마다 살펴 `*.jsonl`을 이름 순서로 하나씩 처리한다.
   - 처리한 파일은 `done/`으로 옮긴다. 정답에 없는 요청은 보내지 않고 로그에만 남긴다(ADR-006).
   - 형식이 틀린 파일은 아무것도 보내지 않고(ADR-008 결정 2) `failed/`로 옮기며, 까닭(줄 번호)을 `failed/<이름>.error`에 쓴다.
   - 다 쓴 파일만 처리하도록, 플랫폼은 다른 이름(`.tmp` 등)으로 쓰고 `*.jsonl`로 바꿔 넣는다. 이름은 플랫폼이 겹치지 않게 짓는다(같은 이름이면 `done/`의 앞 파일을 덮는다).
   - 컨테이너가 멈출 때(SIGTERM) 처리 중인 파일은 끝내고 나간다. 재발행을 쓴 뒤 옮기기 전에 죽으면 다음에 한 번 더 보낸다(at-least-once, 받는 쪽은 `event_id`로 중복을 지운다).
3. **처리 시각 = 방출 로그의 가장 늦은 도착 시각 + 1초**: 재발행본의 `emitted_at`은 원천의 가상 시각을 따라야 한다. 방출기가 쓴 방출 로그(Kafka로 보낼 때는 `--copy-dir` 사본)의 마지막 날짜 디렉터리에서 가장 늦은 `emitted_at`을 읽는다. 재발행 파일도 같은 디렉터리에 쓰이므로 요청마다 1초씩 늘고 파일 이름이 겹치지 않는다. 방출 로그가 비어 있으면 처리하지 않고 기다린다.
4. **재발행도 Kafka로**(11단계): `emitter.replay`와 재발행 서비스에 `--sink kafka`, `--bootstrap`을 둔다. 처음 방출과 같은 토픽(`<source>.events`)·키(`entity_key`)·메시지 시각(`emitted_at`)이고, 브로커가 내려가면 기다린다(ADR-007 결정 3·4).
   - 순서: 보내고 → 브로커 확인(`flush`) → 방출 로그(사본)에 쓰고 → 요청을 `done/`으로 옮긴다. 확인 전에 실패하면 사본도 쓰지 않고 요청도 그대로 둔다.
   - 보낸 뒤 사본을 쓰기 전에 멈추면, 처리 시각이 그대로라 같은 `event_id`·`emitted_at`으로 한 번 더 간다.
5. **이 레포의 compose는 개발용**: `docker compose --profile source up --build`가 `sim`(끝나면 멈춤) → `emitter`(Redpanda로) · `replay`(`out/requests/` 살펴보기)를 띄운다. Redpanda에 컨테이너용 주소 `redpanda:29092`를 더했다. 운영 배치(볼륨 경로, 브로커 주소)는 플랫폼 compose가 명령 인수로 정한다(ADR-007).

## 결과

- 확인: 시드 0, 5년을 compose로 돌려 Kafka로 60,588개(방출 56,096 + 마감 집계)가 나갔다. 누락 5개 요청은 `done/`으로 옮겨지고 `dt=2031-11-02/part-replay-20311102T002732.jsonl`로 재발행됐다. `seq` 0 요청은 `failed/`로 가고 `.error`에 `:1: 재발행 요청 형식이 아니다`가 남았다. `docker compose stop`에 종료 코드 0으로 끝났다.
- 확인(11단계): 같은 실행에서 누락 266개를 요청 파일 하나로 넣자 재발행 서비스가 Kafka로 보냈다. 토픽 `*.events`는 56,362개(방출 56,096 + 재발행 266)이고 정답 55,803개가 모두 있다.
- 완료 기준은 `tests/test_replay_service.py`가 보인다: 처리 시각, 요청마다 다른 시각·파일, 틀린 요청은 보내지 않고 까닭을 남김, 방출 로그가 비면 기다림, 쓰는 중인 파일(`.tmp`)과 쓰는 중인 줄은 건너뜀, Kafka로는 같은 토픽·키로 보내고 사본을 쓰며 전달에 실패하면 사본도 옮기기도 하지 않음.
- `sim`은 `--forever`가 아니다. 끝없는 정답 로그를 방출기가 따라 읽는 것은 12단계다.
- 다루지 않는 것
  - 이미지 레지스트리 배포. 플랫폼 compose는 `build:`에 이 레포(태그)를 가리켜 빌드한다.
  - 요청 처리 결과를 플랫폼에 따로 알리는 파일. `done/`·`failed/`로 옮긴 것과 `.error`가 전부다.
  - 컨테이너 사용자. 기본(root)으로 돌아 공유 디렉터리의 파일을 옮길 수 있다.
