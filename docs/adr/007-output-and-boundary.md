# ADR-007 출력 방식과 경계

- 상태: 확정
- 날짜: 2026-10-27

## 맥락

방출 로그는 날짜별 JSONL 파일로만 나간다. 플랫폼이 스트리밍 수집을 연습하려면 Kafka 호환 브로커로도 받을 수 있어야 한다.
그런데 브로커로 바로 보내면, 브로커가 내려가 있을 때 클라이언트가 전달 제한 시간 뒤 메시지를 버린다. 그러면 의도한 노이즈와 구별되지 않는 누락이 생겨 채점이 틀어진다.
또 `out/emitted`를 누가 관리하는지(원천인가 플랫폼인가)가 정해져 있지 않다.

## 결정

1. **경계**
   - **정답 로그**(`out/truth`)는 원천 시스템의 기록이다. 원천(시뮬레이터)이 보존한다.
   - **방출기**는 원천 → 플랫폼 사이의 전송 구간을 흉내 낸다. 지연·중복·누락은 여기서 생긴다.
   - **착륙 구역**부터는 플랫폼이다. 파일 모드에서는 `out/emitted` 디렉터리, Kafka 모드에서는 토픽이다. 시뮬레이터는 착륙 구역에 쓰기만 한다. 보존 기간, 정리, 어디까지 수집했는지는 플랫폼이 관리한다. 재발행(`emitter.replay`)은 원천이 착륙 구역에 다시 보내는 것이다.
   - 마감 집계(ADR-006)는 원천이 내고, 대사는 플랫폼이 한다.
2. **출력 방식은 둘**: `file`(기본, 날짜별 파일)과 `kafka`. 정답 로그는 어느 방식에서든 파일이다(채점과 재현의 기준).
3. **Kafka 토픽과 메시지**
   - 토픽: 출처 시스템별 `<source>.events`(예: `mes.events`), 마감 집계는 `<source>.manifest`
   - 키: `entity_key`. 같은 개체는 같은 파티션에 들어가 파티션 안에서는 도착 순서가 지켜진다.
   - 값: 봉투 JSON 그대로. 메시지 타임스탬프 = `emitted_at`
   - 브로커는 플랫폼 소유다. 토픽 만들기와 파티션 수도 플랫폼이 정한다. 방출기는 `--bootstrap`으로 받은 브로커에 쓰기만 한다.
   - 이 레포의 Redpanda(`docker-compose.yml`)는 원천이 프로듀서를 개발·테스트할 때만 쓰는 것이고, 토픽을 자동으로 만든다. 플랫폼과 함께 돌릴 때는 플랫폼의 브로커로 보낸다.
4. **브로커가 없거나 내려가면 기다린다**: 메시지를 버리지 않는다. 전달 제한 시간을 두지 않고(`message.timeout.ms=0`), 멱등 프로듀서(`enable.idempotence`)로 재시도 중복을 막고, 버퍼가 차면 비워질 때까지 기다린다. 시뮬레이션 시계는 가상이라 기다려도 이벤트 시각은 바뀌지 않는다.
5. **멈췄다 다시 켜면 체크포인트에서 이어 보낸다**
   - 체크포인트 = 읽은 정답 이벤트 수 + 방출기 상태(지연 중인 이벤트 힙, 마감 집계 상태). 버퍼를 모두 비워(`flush`) 브로커 확인을 받은 시점에만 저장한다. 하루 마감마다 저장한다.
   - 다시 켜면 체크포인트의 상태를 불러오고, 정답 로그에서 그만큼 건너뛴 뒤 이어서 읽는다. 노이즈는 이벤트별 난수라(ADR-005) 끊김 없이 돈 것과 같은 메시지가 나간다.
   - 마지막 체크포인트 뒤에 보냈지만 기록하지 못한 메시지는 한 번 더 갈 수 있다(at-least-once). `event_id`가 같아 중복 제거로 처리된다. 방출기는 다시 보낸 범위를 출력해 채점에서 가려낼 수 있게 한다.
6. **채점용 사본**: Kafka 모드에서도 `--copy-dir`을 주면 같은 메시지를 도착 순서대로 파일에 함께 쓴다. 리포트는 이 사본으로 채점한다. 사본은 시뮬레이터의 채점 자료이지 플랫폼의 데이터가 아니다.

## 결과

- 플랫폼은 파일(배치)과 Kafka(스트리밍) 중 연습할 수집 방식을 고른다. 노이즈와 마감 집계는 같다.
- 브로커 장애는 데이터 손실이 아니라 지연으로만 나타난다.
- Kafka 클라이언트(`confluent-kafka`)는 선택 의존성이다. 파일 모드만 쓰면 설치하지 않아도 된다.
- 재발행을 Kafka로 보내는 것, 원천 DB를 흉내 내 플랫폼이 직접 조회하는 대사(가져오기)는 다루지 않는다.
